## 一、选题背景与需求分析

### 1.1 背景

AI 编程助手已成为软件开发的重要工具。主流产品多以云端服务、Web 或 CLI 形态存在：云端形态将代码与上下文上传到服务端，存在数据安全与隐私顾虑；CLI 形态对非专业用户不友好；Web 形态在本地文件访问、终端操作、长时间后台任务方面受限。

本项目选题为：**在桌面端构建一个功能完备、可本地控制权限与沙箱、具备多智能体与工具编排能力的 Agentic 编程助手（Auraxis）**。系统以 Electron 单体内核承载本地工具执行能力，通过权限管控与原生沙箱把「模型能做什么」限制在用户授权范围内，并把对话、思考、工具调用统一记录为可回放的会话事件日志。

### 1.2 研究意义

- **实用价值**：提供本地优先的编程助手，支持文件读写、终端、SSH、Web 检索等 63 个工具，可完成真实编码任务；除调用 LLM API 外核心能力可离线运行。
- **安全价值**：将「权限三模式 + 权限 Profile + 原生沙箱 + read-before-write 观测」作为工具执行硬边界，为 Agent 类应用的权限模型提供可复用的实现参考。
- **工程价值**：统一 ReAct 步进引擎、统一会话事件日志、可替换接口（SessionStore / ShellExecutor / LlmAdapter）等设计，体现「单一事实源」与「可测试性」的工程思想。

### 1.3 国内外研究现状（写作提示）

### 1.4 主要研究内容

1. 研究 Agent 循环的统一抽象：聊天与 Agent 任务共用一套步进引擎；
2. 研究模型工具的执行管线与权限模型：审批、沙箱、冲突锁、撤销、观测；
3. 研究多智能体调度：优先级队列、并发控制、暂停/恢复、子任务分叉；
4. 研究会话持久化与检索：统一事件日志、投影缓存、FTS5 全文检索、长期记忆；
5. 研究桌面端工程化：IPC 边界、跨进程类型契约、自动化测试与覆盖率门禁。

## 三、系统总体设计

### 3.1 设计目标与原则

- **统一循环**：聊天与 Agent 共用 step-engine，差异用策略钩子表达；
- **单一事实源**：跨进程类型只定义在 `electron/contracts/`，两端 re-export；
- **安全纵深**：权限 Profile → 沙箱门 → 规则匹配 → 审批 → worktree 重定向 → 冲突锁 → 执行 → 观测，顺序不可绕过；
- **可替换 seam**：SessionStore / ShellExecutor / LlmAdapter 三个接口可替换实现；
- **可测试**：纯逻辑抽成可测函数，依赖 Electron 的模块用 `vi.mock` 隔离。

### 3.2 总体架构

```text
┌─────────────────────────── Electron Main ───────────────────────────┐
│ 窗口/安全(CSP) │ IPC 总线 │ 统一步进引擎 │ 工具执行管线 │ 权限/沙箱   │
│ Agent 调度器  │ 会话事件日志 │ 记忆/FTS │ 终端/SSH │ ACP/SDK/headless │
└───────────────────────────────┬────────────────────────────────────┘
                                │ contextBridge / IPC
┌───────────────────────────────▼────────────────────────────────────┐
│ React 18 + AntD + Zustand（消息/输入/工作台/设置/终端/时间轴）      │
└────────────────────────────────────────────────────────────────────┘
```

采用双进程模型：Node 能力只允许在主进程（`electron/`）执行，渲染进程（`src/`）经 `preload.ts` 暴露的 `window.electronAPI` 走 IPC，禁止在渲染层 require Node 模块。生产环境启用严格 CSP，API Key 等敏感信息仅存主进程。

### 3.3 模块划分

| 层 | 模块 | 职责 |
|---|---|---|
| 主进程 | step-engine / query-engine / agent-loop | 统一 ReAct 步进、聊天与 Agent 两条驱动 |
| 主进程 | tool-defs / tool-handlers / tool-runner | 63 个工具定义、执行、批量与并发调度 |
| 主进程 | permission-handlers / permission-profile / sandbox-runner | 权限三模式、Profile、原生沙箱 |
| 主进程 | session-store / chat-log / session-log / fts | 统一事件日志、投影、全文检索 |
| 主进程 | code-mode / fork-runner / schedule-store / conflict-detector | Code Mode、分叉、跟进任务、冲突锁 |
| 主进程 | memory-db / memory-extractor / settings-store | 长期记忆、记忆提取、加密设置 |
| 主进程 | sdk-server / acp-server / headless-run | 对外接口与无头执行 |
| 渲染层 | components（chat/input/layout/agent/settings/tools…） | 界面与交互 |
| 渲染层 | stores（17 个 Zustand Store） | 状态管理 |
| 扩展 | packages/auraxis-sdk / python/auraxis_sdk | TS / Python 客户端 SDK |

### 3.4 关键数据流

```text
用户输入 → 驱动(聊天/Agent) → step-engine 步进
  → LLM 流式响应 → 工具批 → tool-runner（并发分批）
  → executeToolCall（profile→沙箱→审批→执行→观测）
  → 结果追加事件日志 → 停止策略评估 → 下一轮或结束
```

### 3.5 技术选型

| 选型 | 理由 |
|---|---|
| Electron | 成熟桌面跨平台方案，Node 与 Chromium 同体，便于实现本地工具与安全边界 |
| React 18 + TypeScript | 组件化 UI，类型安全约束跨模块接口 |
| Zustand | 轻量状态管理，配合 persist 中间件完成渲染层缓存 |
| SQLite / JSONL | 结构化投影缓存与 append-only 事件日志互补；JSONL 便于回放与导出 |
| Vitest + @testing-library/react | 主进程 node 环境与渲染进程 jsdom 环境统一测试框架 |
| electron-builder | NSIS / DMG / AppImage 三平台打包 |

## 四、详细设计与关键流程

### 4.1 统一步进引擎

一个 step = 一次 LLM 请求（含重试）+ 一次工具批 + 历史追加 + 停止评估 + 上下文压缩。聊天与 Agent 共用该实现，差异通过策略钩子注入（`onBeforeRequest` / `onToolSummary` / `reviewGate` / `interceptTool` 等）。

```text
loop:
  request = buildRequest(history, hooks.onBeforeRequest)
  response = llm.stream(request)         // 失败重试 ≤3 次
  append user/assistant/thinking 事件
  batch = parseToolCalls(response)
  for each tool: executeToolCall(...)    // 回穿完整管线
  append tool 结果事件
  if stopPolicy(response, state): break  // 含 <FINAL_ANSWER>、计划完成、连续纯文本等
  if tokens/rounds 超限: compress(history)
```

**停止策略**：`<FINAL_ANSWER>` 标记、max_tokens 强制继续、计划项全部 completed、连续 5 轮无工具调用、连续 2 次空响应。

### 4.2 工具执行与权限管线（重点阐述）

63 个工具的定义集中在 `electron/tool-defs.ts`（schema + 并发安全性），处理器在 `electron/ipc/tool-handlers.ts` 注册，执行统一走 `tool-runner.ts → executeToolCall`。新增工具必须同时改定义、处理器与权限门禁三处。

执行顺序（不可绕过）：

```text
权限 Profile 硬边界 → 沙箱门（先于审批失败）→ 规则匹配
  → 模式感知自动批准/对话框（ask/plan/afe）
  → worktree 重定向（若已进入隔离工作区）
  → 撤销备份 + 多 Agent 冲突锁（写类工具）
  → 执行 → 观测登记（read-before-write 记录）
```

**read-before-write**：存在文件的 Write/Edit 必须先 Read（或携带其 version）；Read/Write/Edit 成功都会登记会话级观测，`autoApprove` 无头流程按惯例豁免。路径类工具一律过 `resolveToolPath` / `isPathInside` 边界与 `isSafeExtension` 检查。

### 4.3 多智能体调度与冲突控制

- 三种内置 Agent：Explore（只读）、Plan（只读架构师）、general-purpose（全能力）；
- 单例 `AgentScheduler`：优先级队列 high(3) / normal(2) / low(1)，默认最大并发 3；
- 状态机：idle → queued → running → completed / error / stopped / paused；
- 迭代上限：业务默认 200 次，安全硬上限 500 次；
- 隔离：仅 Git 仓库可用 `EnterWorktree` 在 `.auraxis-sandbox/task-<id>` 创建独立工作区，后续文件/命令自动重定向，启动时回收孤儿沙箱；
- 冲突检测：Write/Edit 前获取文件锁，记录「哪个 Agent、何时修改」，通过 `conflict:getConflicts` 暴露给前端。

### 4.4 Code Mode

`RunCode` 的 TypeScript 程序体在工作线程执行，`await tools.Name(args)` 经消息通道提交到主进程：按提交顺序启动、并发安全工具最多 8 路重叠、变异工具串行；每个子调用回穿完整工具管线；支持硬超时与 terminate worker。该设计把「模型编写编排脚本」纳入与普通工具一致的权限与观测体系。

### 4.5 会话事件日志与 lineage

聊天与 Agent 共用统一词表：`user` / `assistant_chunk` / `thinking_chunk` / `tool` / `command` / `system` / `agent_status`。存储为 append-only JSONL（`session-store.ts`），SQLite 投影缓存与 FTS5 索引（`PRAGMA user_version = 1` 版本化），启动时全量重建索引，之后按会话 600ms 防抖增量刷新。会话的投影、回放、分叉、检索、事件级 lineage（turn 划分 + toolCallId 家族）全部由日志派生。

### 4.6 原生沙箱

`sandbox-runner.ts` 提供四后端：Windows restricted token + Job Object、Windows AppContainer、Linux、macOS；语义分 read / workspace-write / full 三档；不可用后端按降级或拒绝策略处理。工作区隔离（worktree）与命令级原生沙箱叠加使用，形成双重边界。

### 4.7 记忆系统

`memory-db.ts` + `memory-extractor.ts`：优先 better-sqlite3（可选原生依赖，缺失回退 JSON 文件）；每次对话完成后由 LLM 提取关键信息并去重；分类为 user / feedback / project / reference；按项目路径隔离；新对话开始时自动注入相关记忆。设置存储使用 Electron `safeStorage` 加密 API Key，旧明文自动迁移。

### 4.8 插件与 MCP

- 插件扩展点：commands、tools、hooks（onToolExecute / onAgentStart / onAgentEnd）、ui；
- 安全模型：源码扫描 8 种危险模式（eval、new Function、child_process、fs、非本地 fetch、net/os/path）、结构验证、路径白名单、用户确认、API Key 隔离、权限遵循；
- MCP：JSON-RPC over stdio；连接前校验服务器命令；工具发现与调用（`mcp__server__tool` 命名）；状态管理。

### 4.9 前端设计与 Aura 设计系统

渲染层使用 17 个 Zustand Store 管理状态，会话/设置/插件状态以主进程为权威，localStorage 仅作渲染层缓存。布局上消息区占满主聊天区，输入 Dock 与顶部头栏为悬浮层，消息流上下淡出；消息列表用 Virtuoso 虚拟化并测量 Header/Footer 高度保证首尾消息可完整滚出。Aura 设计系统规定品牌黑/象牙白主色、六档圆角、hairline 边框、零位移动画、36px 控件高度与统一图标语义。

## 六、部署与运行手册

### 6.1 环境要求

- Node.js 22.12+（本项目在 Node 24 上验证），npm 10+
- 打包原生依赖（better-sqlite3 / node-pty）需本机 Python 与 C++ 工具链；仅开发运行可不装 better-sqlite3（自动回退 JSON）

### 6.2 开发运行

```bash
npm install
copy .env.example .env        # 或 cp .env.example .env
# 填写 DEEPSEEK_API_KEY（或 OpenAI/Anthropic 兼容端点）
npm run electron:dev          # 开发（主进程编译 + Vite + Electron）
```

### 6.3 生产构建

```bash
npm run build                 # 产出 NSIS / DMG / AppImage 安装包到 release/
```

### 6.4 无头与 SDK

```bash
npm run cli -- --run "<任务>" --project <路径> --mode afe
npm run cli -- --sdk          # JSON-RPC over 回环 TCP
npm run cli -- --acp
```

TS SDK：`npm run sdk:build`；Python SDK：`pip install -e ./python/auraxis_sdk`。

### 6.5 常见问题

| 现象 | 处理 |
